# bAIos FPM DRAM Timing Presets

This document defines sane default timing presets for **60 ns** and **70 ns** FPM SIMMs at **25 MHz** and **33 MHz** host-bus speeds.

The goal is not to expose every theoretically valid combination. The goal is to give bAIos a small set of presets that:

- match the timing behavior of the VL82C486 memory controller;
- are reasonable for ordinary 60 ns / 70 ns FPM SIMMs;
- favor useful page-mode performance instead of blindly making every field as small as possible;
- avoid unnecessarily using a 2T CAS write pulse;
- leave the existing manual controls available for expert tuning.

## Timing notation

bAIos exposes:

- **RAS Precharge**: `TRP`, 1T–4T
- **RAS to CAS Delay**: `TRCD`, 1T–4T
- **CAS Width**: read/write

This document writes a profile as:

```text
TRP-TRCD-CASread/CASwrite
```

Example:

```text
2-2-2/1
```

means:

```text
RAS Precharge : 2T
RAS-to-CAS    : 2T
CAS Read      : 2T
CAS Write     : 1T
```

## Important L2-cache display behavior

The current bAIos UI appears to report an extra read clock when L2 cache is enabled.

Therefore a raw memory-controller setting such as:

```text
2-2-2/1
```

may be displayed by bAIos with L2 enabled as:

```text
2-2-3/1
```

That extra T should be treated as an **L2/cache-miss cycle-start penalty**, not as an actual 3T CAS pulse.

For preset implementation, store the **raw controller timing** and derive the displayed/effective timing separately.

# Recommended presets

## Primary preset matrix

| Bus | DRAM | Raw preset | With current L2-aware display | Notes |
|---|---|---:|---:|---|
| 25 MHz | 60 ns | **1-2-1/1** | **1-2-2/1** | Fast page-mode CAS; extra RCD gives margin for first-access/interleaved timing |
| 25 MHz | 70 ns | **2-1-2/1** | **2-1-3/1** | 70 ns needs more RAS-precharge time and cannot safely use the shortest CAS read |
| 33 MHz | 60 ns | **2-1-2/1** | **2-1-3/1** | One RCD clock is sufficient for 60 ns parts when using the 2T CAS read |
| 33 MHz | 70 ns | **2-2-2/1** | **2-2-3/1** | Recommended general-purpose 33 MHz / 70 ns setting; matches observed good behavior |

These should be the normal bAIos presets.

# Preset definitions for Codex

```c
// Raw VL82C486-style DRAM timings.
// Display code may add the existing L2 read-cycle offset separately.

25 MHz / 60 ns:
    ras_precharge = 1;
    ras_to_cas    = 2;
    cas_read      = 1;
    cas_write     = 1;

25 MHz / 70 ns:
    ras_precharge = 2;
    ras_to_cas    = 1;
    cas_read      = 2;
    cas_write     = 1;

33 MHz / 60 ns:
    ras_precharge = 2;
    ras_to_cas    = 1;
    cas_read      = 2;
    cas_write     = 1;

33 MHz / 70 ns:
    ras_precharge = 2;
    ras_to_cas    = 2;
    cas_read      = 2;
    cas_write     = 1;
```

A simple lookup structure would be sufficient:

```c
struct DramTimingPreset {
    unsigned bus_mhz;
    unsigned dram_ns;
    unsigned trp;
    unsigned trcd;
    unsigned cas_read;
    unsigned cas_write;
};

static const struct DramTimingPreset fpm_presets[] = {
    { 25, 60, 1, 2, 1, 1 },
    { 25, 70, 2, 1, 2, 1 },
    { 33, 60, 2, 1, 2, 1 },
    { 33, 70, 2, 2, 2, 1 },
};
```

# Why these pairings are not monotonic

The settings should **not** be generated by simply lowering every timing until the machine becomes unstable.

RAS-to-CAS delay and CAS width trade time against each other during the initial row access.

For example, at 33 MHz:

```text
60 ns: 2-1-2/1
70 ns: 2-2-2/1
```

The 60 ns part can tolerate the shorter RAS-to-CAS delay because its access-time requirement is tighter.

At 25 MHz / 60 ns, this preset is intentionally:

```text
1-2-1/1
```

rather than:

```text
1-1-2/1
```

The first form keeps the **page-mode CAS path at 1T**, which is valuable for repeated accesses within an already-open row, while placing the extra clock on the RAS-to-CAS portion of a new-row access.

This is why timing fields should be treated as a **coherent profile**, not four independent "lower is always faster" sliders.

---

# CAS write recommendation

Use:

```text
CAS Write = 1T
```

for all four normal presets.

A 2T CAS write width should be reserved as a **compatibility fallback**, not selected merely because CAS read is 2T.

This also matches the observed result that:

```text
2-2-3/1
```

performs substantially better than:

```text
2-2-3/2
```

when L2 is enabled.

Do not automatically couple read and write CAS widths.

# Optional compatibility presets

If bAIos offers a separate **Safe/Compatibility** mode, use one additional T where it provides broadly useful margin rather than slowing every field indiscriminately.

Suggested fallbacks:

| Bus | DRAM | Normal | Compatibility |
|---|---|---:|---:|
| 25 MHz | 60 ns | `1-2-1/1` | `2-2-2/1` |
| 25 MHz | 70 ns | `2-1-2/1` | `2-2-2/1` |
| 33 MHz | 60 ns | `2-1-2/1` | `2-2-2/1` |
| 33 MHz | 70 ns | `2-2-2/1` | `3-2-2/1` |

If a particular board or SIMM still misbehaves, manual timing controls remain the final fallback.

Avoid changing CAS write to 2T unless testing shows an actual write-related stability problem.

---

# Optional aggressive preset

Only one combination is worth exposing as an explicitly aggressive option:

```text
25 MHz / 60 ns: 1-1-1/1
```

This is very close to the edge of the published timing envelope and should **not** be the default, especially if memory interleaving is active.

Label it something like:

```text
Aggressive
```

or:

```text
60 ns Fast
```

rather than silently selecting it.

For 33 MHz operation, the recommended presets above are already aggressive enough for a general-purpose BIOS default.

# Suggested bAIos UI

A simple selector could be:

```text
DRAM Speed       [ 60 ns ]
Memory Timing    [ Auto  ]
```

Where `Auto` selects from the matrix using the detected/configured bus clock.

Optional values:

```text
Memory Timing    [ Auto          ]
                 [ Compatibility ]
                 [ Manual        ]
```

If the BIOS cannot reliably determine SIMM speed, keep DRAM speed user-selectable:

```text
DRAM Speed       [ 60 ns ]
                 [ 70 ns ]
                 [ Unknown ]
```

For `Unknown`, use the **70 ns** profile.

# Implementation rules

1. Presets should write the **raw memory-controller timings**.
2. Do not encode the L2 cache startup delay into the CAS register value.
3. If bAIos wants to show an effective timing string, calculate that separately.
4. Do not automatically tie CAS read width to CAS write width.
5. Default CAS write to **1T**.
6. Treat the four timing controls as a preset tuple.
7. Changing one field manually should switch the timing mode to `Manual`.
8. If DRAM speed is unknown, assume **70 ns**.
9. If bus speed is between supported presets, select the next more conservative known profile rather than extrapolating.
10. These presets are intended for ordinary **FPM DRAM**, not EDO.

# Expected effective strings with L2 enabled

Assuming the current bAIos behavior adds one effective T to the read side when external L2 is enabled:

| Bus | DRAM | Raw | Effective/displayed with L2 |
|---|---|---|---|
| 25 MHz | 60 ns | `1-2-1/1` | `1-2-2/1` |
| 25 MHz | 70 ns | `2-1-2/1` | `2-1-3/1` |
| 33 MHz | 60 ns | `2-1-2/1` | `2-1-3/1` |
| 33 MHz | 70 ns | `2-2-2/1` | `2-2-3/1` |

This makes the observed:

```text
2-2-3/1
```

a sensible default for **33 MHz + 70 ns FPM + L2 enabled**.

# Source basis

The preset logic is based primarily on:

- **VLSI Technology VL82C486 Data Manual, June 1992**, especially the RAM timing register and Table 18, "Calculation of DRAM Speed Requirements".
- Period FPM DRAM/SIMM timing specifications for 60 ns and 70 ns parts.

VL82C486 manual:

https://bitsavers.computerhistory.org/components/vti/pc/VTI_VL82C486_Data_Manual_199206.pdf

The key point from the chipset documentation is that acceptable DRAM speed depends on the **combination** of RAS precharge, RAS-to-CAS delay, CAS width, cycle-start timing, and interleaving—not on any one field in isolation.
