# SL and SMM implementation reference

This developer record contains board contracts, diagnostic codes and validation detail. User instructions are in the [port manual](../../README.md) and [shared power-saving guide](../../../docs/sl486-support.md).

## Current idle implementation

Version0.14.8 adds the nonprivileged APM caller needed under EMM386. Cache operations run inside the handler. Version0.14.6 removed the divider gate: every doze/suspend request and wake write preserves the actual PCI divider. Runtime qualification requires the installed SMM handler and its Intel-compatible controller save-state interface. These replace the earlier HLT-only and PCI /1 restrictions in the reference notes below.

The native APM idle provider uses doze, waits for an unmasked pending interrupt, restores native full-on state and cache state, then hands off the interrupt. The controlled RTC diagnostic retains its separate suspend request. The tested0.14.4 keyboard result is K0 with sustained altered chipset signals and working subsequent floppy reads. Later source checks do not establish physical results for other dividers.

The following sections preserve the earlier source investigation and diagnostic interfaces. Current idle policy is described above. Earlier claims of HLT-only behavior, a missing backend or a required PCI /1 value are superseded.

# SL-enhanced 486 support

Shared code provides CPU qualification, SMM installation and handler services, and an optional Stop Grant idle path through board adapters. System Management Mode (SMM) is a separate processor execution mode. M919 automatically activates its software-SMI handler on qualified Intel desktop SL and Am5x86 CPUs with a supported UMC controller. Its APM CPU Idle path requests chipset doze and restores full speed before interrupt delivery. Timer wake, keyboard wake and subsequent floppy reads work on the tested M919. CPU identification alone does not establish board wiring or physical stability on other configurations.

POST and Setup show `486SX-SL`, `486DX2-SL`, `486SX2-SL`, or `486DX4-SL` for qualified Intel desktop identities. M919 shows `AMD 5x86 SL Enhanced` for qualified Am5x86 identities. The text stays on the existing CPU identity line. The original mobile `486SL` remains separate. These names describe CPU capability, not the current power state or successful motherboard activation.

## DOS idle operation

The M919 enters doze when software calls APM CPU Idle, `INT 15h AX=5305h`. The caller must connect to APM first. Power management must be enabled and engaged. The SMM handler must be ready, with the supported controller interface and PCI / 1 clock selection. If that board path is unavailable, shared code uses its ordinary HLT wait. A disabled APM policy performs no sleep.

For normal MS-DOS 6.22 use, load POWER.EXE in ADV mode through CONFIG.SYS:

```dos
DEVICE=C:\DOS\POWER.EXE ADV:REG
```

POWER.EXE detects idle activity and calls the APM BIOS. Another APM-aware idle driver can supply the same calls. IDLECHK supplies its own calls and needs no POWER.EXE. The BIOS has no automatic inactivity timer. A busy application does not enter this path unless software reports idle time. See the [Microsoft POWER.EXE help](https://www.infania.net/misc/dos622help/power.exe.html) and [Microsoft article Q96560](https://www.infania.net/ms6kb/Q96560.htm).

An enabled hardware interrupt ends each idle wait. Ordinary DOS timer ticks therefore produce brief waits. `IDLECHK K` masks the timer interrupt to hold the state until keyboard wake or its diagnostic watchdog. The handler ignores masked requests and an empty slave-controller cascade. It restores full speed and cache state before the pending interrupt receives service. The tested keyboard case returns K0 and leaves floppy reads working.

This is CPU idle doze. It does not suspend the whole computer, turn off devices, or install a standby-switch policy. The APM caller issues the software request without privileged cache or CR0 instructions, including under EMM386. The installed SMM handler drains dirty cache data, disables caches during the request, restores L2, invalidates clean tags and restores its CR0 before RSM. The final handler starts at A8000 in the normally uncacheable VGA aperture; bootstrap relocation retains its original caches-off wrapper.

The user reports working DOS and Windows operation and floppy access, with and without Microsoft EMM386, on the 0.14.8 candidate. Under Windows 3.1 with its APM driver and Advanced selected, U10 pin51 changes while pin33 appears high. This establishes the reported clock behavior, not a measured Stop Grant acknowledgment. The earlier sustained keyboard diagnostic remains a separate observation.

## Query contract

Call `board_cpu_sl_query` from board-owned code. Do not call the private shared `cpu_detect_sl` or `cpu_query_identity` helpers from generic firmware.

| Result | Meaning |
| --- | --- |
| AX = 0 | CPU SL capability is unknown from the supported observations. This does not prove absence. |
| AX = 1 | The CPU matches a documented Intel desktop SL Technology candidate. This does not qualify motherboard wiring. |
| AX = 2 | A documented Am5x86 identity supports the standard two-pin SMM format. This does not qualify motherboard wiring. |
| DX = 0 | No board SL function is ready. |
| DX = 1 | M919 installed, relocated and pinged its SMM handler during this boot. |

The adapter preserves every other register, upper EAX and EDX, and all EFLAGS. The query needs no input. M919 reads this boot's readiness through the current BDA EBDA pointer. The query uses temporary stack space. It performs no configuration I/O, cache operation, control-register change, SMI generation, clock operation, or reset operation. Presentation calls `board_cpu_detect_name`, which preserves the existing CS:SI name contract and classifies the CPU without hardware access.

The private shared query changes AX only. Each board adapter supplies DX independently. M919 separates the live pre-install qualification from the final readiness result. The other ports return DX zero. CPU qualification alone cannot supply board permission.

## Identification evidence

The query first requires writable EFLAGS.ID, a CPUID leaf-zero maximum of at least one, and the complete `GenuineIntel` vendor string. It then accepts original processor type zero, family four, and models 2, 3, 5, 7, or 8. The stepping does not change this candidate result. Reserved signature and feature bits do not determine it.

This classification combines two primary sources. Intel's [1995 processor family data book](https://bitsavers.trailing-edge.com/components/intel/80486/241731-002_Intel486_Microprocessors_and_Related_Products_1995.pdf), section 2.1, describes the current desktop SL families. [AP-485, December 1996](https://bitsavers.org/components/intel/appNotes/AP-485_Intel_Processor_Identification_and_the_CPUID_Instruction_Dec96.pdf), section 3.2, states that older SX and DX2 versions lack CPUID. It also states that SL-enhanced versions support CPUID. This is a bounded inference about the named families. It is not a direct CPUID SL feature flag.

| Observation | Result and reason |
| --- | --- |
| Intel CPUID models 2/3/5/7/8 | Desktop SX, DX2, SX2, write-back DX2, and DX4 candidate families. |
| Intel DX models 0/1 | Unknown. The family documentation includes a 5 V, 50 MHz DX without SL Technology. |
| Intel model 4 | Unknown for this desktop query. The original mobile 486SL is a distinct processor. Its existing name remains `486SL`. |
| AMD vendor string `AuthenticAMD`, original type zero, family four, models E/F | Profile 2. These Am5x86 identities use the standard two-pin SMM interface. |
| Intel model 9, another type or family, or an unlisted vendor/model | Unknown until the supported evidence list is extended. Unknown does not prove absence of similar features. |
| No CPUID, unavailable leaf 1, or a mismatched vendor byte | Unknown. Do not infer SL support from the retained reset signature or a generic CPU name. |

The data book's Appendix B defines no SL/SMM capability bit. Section 2.1 explicitly excludes the 50 MHz DX from SL Technology. Table 3-1 describes changed package pins for SMI, SMM acknowledgement, soft reset, and stop clock. These facts prevent a universal family-four enable rule.

AMD's [Am5x86 data sheet, 19751 revision C](https://www.amd.com/content/dam/amd/en/documents/archived-tech-docs/datasheets/19751.pdf), section 7.3 and Table 10, documents the compatible save map. Other formats, including legacy UMC and Cyrix, need separate qualification. Ambiguous AMD models 8/9 remain unknown to this query. Traced AMI CPU producers select chipset interface 30h for legacy UMC, correcting the earlier classic-AMD interpretation of that field.

## SMM services

`board_smm_prepare` is the production installation entry. M919 obtains live CPU and controller qualification, then calls the shared installer. Its startup owner opens SMRAM only during early POST, installs both bootstrap and final images, closes the ordinary view, relocates and verifies a fresh ping before publishing readiness. Other ports return AX=1 and CF set before any SMRAM write. Their DX remains zero. Other registers and flags remain unchanged, except the result CF and AX/DX outputs.

The board owns source reservation, destination mapping, protection from ordinary CPU and DMA access, and cache coherency before the first handler fetch. It must latch or defer reset as required by the CPU manual. Installation never enables an SMI source.

`smm_install` accepts AX profile 1/2 and DX bit 0 set. DS:SI points to a nonoverlapping ROM image. ES:DI addresses the opened SMRAM window, with DI=8000h. CX is 2..7E00h. SI+CX must not exceed 10000h. The installer checks these bounds before writing, copies forward, and verifies the bytes. It preserves all registers except AX and all flags except CF, including caller DF. AX=0/CF clear means success. AX=1 means unavailable, AX=2 means invalid bounds, and AX=3 means verification failed. An error sets CF.

The board instantiates `smm_handler entry_label, fixed_target` at SMBASE+8000h. Its stackless `board_smm_ack` macro must acknowledge the actual source and return AL=1 only for the software-command source. Other sources resume without changing the saved CPU state. The handler uses no ordinary BIOS call or interrupted stack.

Software commands require saved EBX=`SMM_REQUEST` (534D4D51h). Saved low CX=0 requests a ping. CX=1 requests relocation, with saved EDI equal to the compiled target. EAX and EDX remain available for the actual I/O trigger. Before requesting relocation, the board must install and protect the target window. The handler requires relocation support in revision bit 17. SMBASE must be 32 KiB aligned and at most F0000h, so the entire window stays below 1 MiB. Invalid compiled targets fail assembly.

A handled command returns saved EBX=`SMM_REPLY` (534D4D52h), ECX=revision, and EAX=status. Status 0 clears saved CF. Status 1 rejects an unknown command, 2 rejects unsupported relocation, and 3 rejects a target mismatch. Errors set saved CF. A missing fresh reply is not success. Only a successful relocation changes the saved SMBASE. The handler preserves I/O restart, halt restart, reserved fields, and the other saved context. RSM resumes execution.

M919 keeps its extension at E0000 and the final hidden handler at SMBASE A0000, entry A8000. Startup copies the E bank's shadow backing before later regional shadow reads can select it. Runtime software commands reject protected/V86 entry before accessing the E bank. The real-mode wrapper saves southbridge A0/A8 and applies the reference control fields 34h/28h only during the request. Their exact individual hardware roles remain unresolved. It pre-arms A3.80 before the A3.40 request edge. The wrapper flushes dirty memory, masks interrupts/NMI and disables L1/L2 without ordinary RAM writes. After the request, it restores A0/A8, caches, CF8 and the board NMI policy. Normal reset owners quiesce the software source in F-bank code, even when E is not decoded. No persistent power manager is enabled.

Run `m919/build/diagnostics/SMMSTATE.COM` in plain DOS after flashing the bench image. It prints `S1` for successful activation, `S0` for an unsupported or inactive path, `S2` for installation/closing failure, `S3` for relocation failure, `S4` for ping failure, or `SX` for an unrecognized ROM/runtime layout. Failure adds a command-error digit: 1 unknown command, 2 unsupported relocation, 3 target mismatch, or 4 no fresh reply. For error 4, two optional trace digits describe the bootstrap and final handler. Each combines entry observed (4), matching request cookie (2), and observed software source (1). Thus `S3400` records no observed entry, while `S3460` records a bootstrap entry with a matching cookie but no software-source indication. F means the final trace was unavailable. Older images without trace validity keep the shorter result. Startup reads markers only after quiescing requests and closes the manual view afterward. The DOS tool changes no hardware and never opens SMRAM. A CPU that enters broken SMM and never returns can still hang before DOS; software cannot recover that failure.

With an SMM-ready M919 image installed, run `m919/build/diagnostics/WAKECHK.COM` in plain DOS. No additional flash is needed. It checks recorded SMM readiness, schedules an RTC alarm two seconds ahead, observes its IRQ8 callback and restores the original inactive alarm, interrupt masks and callback vector. It leaves clocks, caches and SMRAM unchanged. The normal timer bounds the wait to about five seconds, with a finite instruction guard as a second bound.

| Code | Meaning |
| --- | --- |
| W0 | Current SMM status is 1 and the scheduled RTC callback completed, with cleanup. |
| W1 | The ROM/runtime is incompatible or SMM is not ready. |
| W2 | RTC interrupts or another interrupt prerequisite are busy. |
| W3 | RTC validity, time or alarm arming was rejected. |
| W4 | No matching RTC callback arrived within the wait bound. |
| W5 | IRQ8 did not drain. Configuration was restored, but pending interrupt state is not certified. Restart before a clock experiment. |
| WX | Plain real-mode DOS is required. |

W0 qualifies this software wake prerequisite only. It does not test a clock request, prove a Stop Grant bus acknowledgment or measure the external CPU clock. Use a scope or logic analyzer only when software observations leave a necessary electrical question unresolved.

## Opt-in M919 clock experiment

Version 0.13.0 adds `m919/build/diagnostics/CLOCKCHK.COM`. Run it only in plain DOS after SMMSTATE reports S1 and WAKECHK reports W0. It arms a new RTC alarm, calls one board-private SMM request, then restores the captured controller and interrupt settings. Normal POST and APM clock policy remain unchanged. If the clock request does not resume, power the machine off and on.

The trial uses a retained Phoenix native-SMM request. It requires live PCI / 1, ISA PCI / 2 and keyboard 7.16 MHz encodings. It declines if they differ. Keep Current can already produce a matching encoding. The diagnostic does not change Setup or choose a faster bus setting. Report the short code before changing any setting.

| Code | Meaning |
| --- | --- |
| C0 | IRQ8 was pending when the request window ended; the actual alarm callback and cleanup then completed. |
| C6 | The request window continued before the alarm; the callback and cleanup then completed. |
| C1 | The private firmware interface, current SMM readiness, CPU, controller or mode is unavailable. |
| C2 | RTC ownership is busy, or the alarm expired before the request. |
| C3 | RTC validity, time or alarm arming was rejected. |
| C4 | The alarm callback did not arrive within the software wait bound. |
| C5 | IRQ8 did not drain. Restart before another clock experiment. |
| C7 | No fresh software-SMI reply arrived. |
| C8 | The live PCI divider does not match the reference request. |
| C9 | The live ISA or keyboard clock does not match the reference request. |
| CX | Plain real-mode DOS is required. |

C0 and C6 are software observations. Neither proves a Stop Grant acknowledgment or the electrical state of external CPU CLK. The alarm timeout can run only if the CPU resumes. The donor's intermediate full-on transition is retained before restoring the exact entry bytes; peripheral suspend callbacks and persistent power-policy timers are outside this trial.

## Stop Grant and APM

Boards can supply paired inline `board_stop_grant_query` and `board_stop_grant_idle` macros. Both must work in 16-bit and 32-bit code. Query returns CF clear only when the current CPU, wiring, and controller qualify. The provider must preserve segments and stack. Shared code preserves the caller's other state around the provider.

The idle provider owns the complete STPCLK request, Stop Grant acknowledgment, and wake release. Interrupt assertion alone does not release STPCLK. The board must release it before interrupt delivery and preserve the interrupt until acknowledgment. CF-clear return means one completed wake. CF-set decline must precede entry, leave STPCLK released, and consume no wake. Shared code then performs one HLT wait.

The public APM real-mode, protected 16-bit, and protected 32-bit entries use this shared path. Disabled APM Idle performs no query or sleep. Installation can query capability even when policy is disabled, and reports both facts separately. APM installation sets its clock-slowing flag only for a qualified provider. M919 supplies the native doze provider. Other current ports retain HLT. External clock removal, device suspend, and new Setup controls are outside this interface.

The [Stop Grant evidence report](../research/stop-grant.md) covers the larger retained ROM set, the missing pin documentation and the complete Award timer/APM request protocol. Stop Grant remains active work. The earlier HLT finding does not exhaust the available power-state code or establish a lack of hardware support.

## Automated checks

The shared assembled CPU proof executes each actual board adapter. It checks the qualification result, independent CPUID gates, reserved-bit contrasts, misleading reset signatures, caller state, and absence of hardware operations. It also retains the existing name and three rendered-consumer checks.

Run `python -B shared/tools/smm_proof.py` for installer bounds, actual installed handler execution, saved context, replies, and relocation followed by another SMI. Run `python -B shared/tools/stop_grant_proof.py` for paired providers and the public APM entries. These use independent CPU and pin models. They do not emulate physical SMRAM protection, hardware I/O replay, AutoHALT restart, or electrical timing.

Run `python -B m919/tools/smm_activation_proof.py` for the composed startup, live qualifier, actual installer and software trigger, installed handler/RSM, cache restoration, hidden-memory views, E shadow copy, reset and DOS status tool. It builds its own ROM and the status tool. Its PCI, cache and CPU seams remain models, not hardware qualification.

Run `python -B m919/tools/test-clock-check.py` for the complete clock diagnostic, actual SMM wrapper/handler/RSM and actual RTC callback/cleanup path. Its clock behavior is an external model. It checks live-divider declines, expired alarms, immediate continuation, pending-at-return, no reply and exact ordered restoration. It also verifies that the ordinary WAKECHK bytes remain unchanged.

Run `python -B m919/tools/test-wake-check.py` to build WAKECHK and exercise the actual COM, INT1A and int70 paths. DOS vector services and RTC/PIC/timer hardware are modeled. The check covers native RTC formats, midnight rollover, stale and unrelated causes, unavailable inputs, exact restoration and an IRQ8 pending during cancellation. It requires the existing M919 ROM and listing and does not rebuild them.

M919 runs this proof through `python -B m919/tools/test-hardware.py --case cpu`. PB430 and MP386 expose a `cpu` case in their existing `tools/test-port.py` commands. Presario's `tools/test-shared-adoption.py --case cpu` uses the selected `BAIOS_BUILD_DIRECTORY`. The normal automated port checks include CPU coverage. These synthetic observations prove firmware decisions, not physical SL wiring or stability.
